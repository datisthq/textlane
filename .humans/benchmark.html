Benchmark

Markdown to HTML, measured 2026-10-30 on an AMD Ryzen 5 PRO 7545U, 12 threads, 30 GB RAM, Linux 7.0, textlane at commit 0581318. Three cases: cmark, a README in CommonMark; gfm, a README in GFM with every library's GFM extensions on; cmark-full, the CommonMark edge cases of the conformance suite. Raw HTML passes through; median of five runs after one warmup, the tools taking turns run by run, on an idle machine. marked, markdown-it, micromark and unified ran just after the others, with other jobs loading the machine (load average 3–4), so their figures are if anything low. Source: pnpm -C benchmark measure; the method is in benchmark/README.md.

Why textlane is where it is

The parser is a cmark-style one: a pass over the lines with a stack of open blocks, then one pass over each paragraph's text, building mdast as it goes, with no event list between. It still gives micromark's trees and positions exactly, so every unified plugin sees the tree it expects. What it adds over comrak and pulldown-cmark is a second tree: mdast, then hast, then HTML, each a pass of its own, over 112-byte nodes.

Against its own family
unified, micromark and markdown-rs build the same trees through micromark's event engine; textlane is 14× markdown-rs and over 100× unified on the 1 MB README, and unified and micromark time out on 1 MB of edge cases.
Against the fastest
comrak and cmark build a tree too, but render HTML from it directly; pulldown-cmark streams events and builds none. The gap is the same on CommonMark and GFM: building and walking hast is about half of textlane's time, and the time follows node size. On 1 MB of edge cases textlane is level with comrak and cmark, slightly ahead.
GFM
With GFM on, textlane stays level with cmark and 1.7× behind comrak; tables slow comrak as much as textlane, so no GFM construct stands out.
Memory at 10 MB
The six fastest run a 10 MB README too: textlane peaks at 170–220 MB on CommonMark and 290–320 MB on GFM, against 114 and 154 MB for comrak, 139 and 223 MB for cmark and under 50 MB for pulldown-cmark.
Same output as unified
textlane's HTML matches unified's in size on every document unified finished; other libraries differ by a few percent, from their own rendering choices.

Reading the numbers

  • Time is clocked inside each process after imports and reading the file, over at least 8 MB of input per run, and divided per document. The tools take turns run by run, so load from elsewhere falls on all of them.
  • Memory is peak anonymous memory sampled every 50 ms, runtime included: Node.js starts tens of megabytes above Rust, and a run under 50 ms may show none.
  • micromark, markdown-it, pulldown-cmark and markdown-rs build no syntax tree; marked, mistune and Python-Markdown are not CommonMark compliant; pulldown-cmark has no GFM autolink literals. The tables compare speed, not features.
