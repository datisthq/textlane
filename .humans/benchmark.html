Why textlane is where it is

The parser is a cmark-style one: a pass over the lines with a stack of open blocks, then one pass over each paragraph's text, building mdast as it goes, with no event list between. It still gives micromark's trees and positions exactly, so every unified plugin sees the tree it expects. What it adds over comrak and pulldown-cmark is that tree: mdast, then hast, then HTML, each a pass of its own.

Tables are most of the gap
A table cell of a few input bytes becomes hundreds of bytes of tree across mdast and hast, so table-heavy documents outgrow the CPU cache and slow every pass: the README without its tables converts in about 40% less time.
Against its own family
unified, micromark and markdown-rs build the same trees through micromark's event engine; textlane is 22× markdown-rs and 60× unified on the 1 MB README, and unified and micromark time out on 1 MB of edge cases.
Against the fastest
comrak and cmark build a tree too, but render HTML from it directly; pulldown-cmark streams events and builds none. On 1 MB of edge cases textlane is level with comrak and 1.5× cmark.
Memory at 10 MB
The six fastest run a 10 MB README too: textlane peaks at 290–310 MB from each language, against 154 MB for comrak, 225 MB for cmark and 47 MB for pulldown-cmark.
Same output as unified
textlane's HTML matches unified's in size on every document unified finished; other libraries differ by a few percent, from their own rendering choices.

Reading the numbers

  • Time is clocked inside each process after imports and reading the file, over at least 8 MB of input per run, and divided per document.
  • Memory is peak anonymous memory sampled every 50 ms, runtime included: Node.js starts tens of megabytes above Rust, and a run under 50 ms may show none.
  • micromark, markdown-it, pulldown-cmark and markdown-rs build no syntax tree; marked, mistune and Python-Markdown are not CommonMark compliant; pulldown-cmark has no autolink literals. The tables compare speed, not features.
