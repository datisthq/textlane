Benchmark

Markdown to HTML on an AMD Ryzen 5 PRO 7545U, 12 threads, 30 GB RAM, Linux 7.0. Three cases: cmark, a README in CommonMark; gfm, a README in GFM with every library's GFM extensions on; cmark-full, the CommonMark edge cases of the conformance suite. Raw HTML passes through; median of five runs after one warmup, the tools taking turns run by run. The other libraries come from an idle full run on 2026-10-30; textlane was measured the same afternoon at commit a357233, with other jobs loading the machine (load average 2–8), so its figures are if anything low. Each textlane build runs twice: with one tree, mdast, written straight to HTML, and with two, as any HTML plugin between md.toHtml and html.stringify makes it keep hast. The 100 KB README ran last, every library in one quiet run. Source: pnpm -C benchmark measure; the method is in benchmark/README.md.

Why textlane is where it is

The parser is a cmark-style one: a pass over the lines with a stack of open blocks, then one pass over each paragraph's text, building mdast as it goes, with no event list between. It still gives micromark's trees and positions exactly, so every unified plugin sees the tree it expects. When md.toHtml and html.stringify end the pipeline, HTML is written straight from mdast, one tree as in comrak and cmark; an HTML plugin between them needs hast, a second tree.

Against its own family
unified, micromark and markdown-rs build the same trees through micromark's event engine; textlane is 18× markdown-rs and over 100× unified on the 1 MB README, and unified and micromark time out on 1 MB of edge cases.
Against the fastest
With one tree textlane is ahead of comrak and cmark on the 10 KB, 100 KB and 10 MB READMEs (1.2× comrak and 1.4× cmark at 100 KB) and 1.4× ahead on 1 MB of edge cases, and 1.3× behind comrak on the 1 MB README; pulldown-cmark, which builds no tree, stays 2–3× ahead. Parsing is about 80% of textlane's time, writing HTML the rest.
The second tree
Keeping hast costs a third of the throughput on CommonMark: 60 against 94 MB/s on the 1 MB README in Rust, and about 50% more memory.
GFM
The GFM README has footnotes, which the direct writer leaves to hast, so both textlane rows build two trees there: level with each other, 1.3× behind cmark and 2.1× behind comrak.
Memory at 10 MB
The fastest run a 10 MB README too, in one idle run of their own: textlane peaks at 111–147 MB on CommonMark with one tree, level with comrak, 171–215 MB with two, and 270–329 MB on GFM, against 114 and 154 MB for comrak, 139 and 222 MB for cmark and under 50 MB for pulldown-cmark.
Same output as unified
textlane's HTML matches unified's in size on every document unified finished; other libraries differ by a few percent, from their own rendering choices.

Reading the numbers

  • Time is clocked inside each process after imports and reading the file, over at least 8 MB of input per run, and divided per document. The tools take turns run by run, so load from elsewhere falls on all of them.
  • Memory is peak anonymous memory sampled every 50 ms, runtime included: Node.js starts tens of megabytes above Rust, and a run under 50 ms may show none.
  • micromark, markdown-it, pulldown-cmark and markdown-rs build no syntax tree; marked, mistune and Python-Markdown are not CommonMark compliant; pulldown-cmark has no GFM autolink literals. The tables compare speed, not features.
