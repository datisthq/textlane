Why textlane is where it is

Parsing is about 80% of the time (1 MB of prose, best of 30: parse 25 ms, md.toHtml 3.5 ms, html.stringify 2.7 ms). The parser is a port of markdown-rs, itself micromark in Rust: a byte-by-byte state machine that attempts constructs and backtracks, writes an event list, then re-tokenizes document, flow, content and text in layers before building mdast. Its cost is per event, and events come per block and per line, not per byte: the spec case, thousands of tiny edge-case blocks, writes about one event per input byte against prose's one per five, so it runs at 3–5 MB/s.

Against its own family
The same design as markdown-rs and micromark, 7–9× and 30–80× faster than them; unified and micromark time out on 1 MB of edge cases.
Against the fastest
comrak, cmark and pulldown-cmark parse in one hand-written pass. Closing that gap means trimming per-attempt overhead in the tokenizer, or a parser of that kind, which risks micromark-exact output and the extension model.
Across languages
The bindings add little: Node.js and Python stay within 20% of Rust on 1 MB and within 5% at 4 MB.
Same output as unified
textlane's HTML matches unified's in size on every document unified finished; other libraries differ by a few percent, from their own rendering choices.

Reading the numbers

  • Time is clocked inside each process after imports and reading the file, over at least 8 MB of input per run, and divided per document.
  • Memory is peak anonymous memory sampled every 50 ms, runtime included: Node.js starts tens of megabytes above Rust, and a run under 50 ms may show none.
  • micromark, markdown-it, pulldown-cmark and markdown-rs build no syntax tree; marked, mistune and Python-Markdown are not CommonMark compliant. The tables compare speed, not features.
