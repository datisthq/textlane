Benchmark

Markdown to HTML on an AMD Ryzen 5 PRO 7545U, 12 threads, 30 GB RAM, Linux 7.0. Three cases: cmark, a README in CommonMark; gfm, a README in GFM with every library's GFM extensions on; cmark-full, the CommonMark edge cases of the conformance suite. Raw HTML passes through; median of five runs after one warmup, the tools taking turns run by run. The other libraries come from idle runs on 2026-10-30; textlane was measured on 2026-10-31 at commit da384e7, with the machine lightly loaded (load average 1–2). Each textlane build runs twice: with one tree, mdast, written straight to HTML, and with two, as any HTML plugin between md.toHtml and html.stringify makes it keep hast. Source: pnpm -C benchmark measure; the method is in benchmark/README.md.

Why textlane is where it is

The parser is a cmark-style one: a pass over the lines with a stack of open blocks, then one pass over each paragraph's text, building mdast as it goes, with no event list between. It still gives micromark's trees and positions exactly, so every unified plugin sees the tree it expects. When md.toHtml and html.stringify end the pipeline, HTML is written straight from mdast, one tree as in comrak and cmark; an HTML plugin between them needs hast, a second tree.

Against its own family
unified, micromark and markdown-rs build the same trees through micromark's event engine; textlane is 24× markdown-rs and over 100× unified on the 1 MB README, and unified and micromark time out on 1 MB of edge cases.
Against the fastest
With one tree textlane is ahead of comrak and cmark on every CommonMark document: 1.05× comrak and 1.2× cmark on the 1 MB README, 1.6× both on 1 MB of edge cases. pulldown-cmark, which builds no tree, stays 1.6–2.8× ahead. From Node.js and Python textlane runs within about a fifth of Rust.
The second tree
Keeping hast costs 40% of the throughput on the 1 MB README in Rust, 75 against 125 MB/s, and about half as much memory again. With it textlane is still ahead of cmark up to 100 KB and behind it from 1 MB.
GFM
The GFM README has footnotes, which the direct writer leaves to hast, so both textlane rows build two trees there: level with cmark and 1.6× behind comrak.
Memory at 10 MB
The fastest run a 10 MB README too: textlane peaks at 113–148 MB on CommonMark with one tree, level with comrak's 114 MB, 172–211 MB with two, and 271–329 MB on GFM, against 154 MB for comrak and 139 and 222 MB for cmark on the two; pulldown-cmark stays under 50 MB.
Same output as unified
textlane's HTML matches unified's in size on every document unified finished; other libraries differ by a few percent, from their own rendering choices.

Reading the numbers

  • Time is clocked inside each process after imports and reading the file, over at least 8 MB of input per run, and divided per document. The tools take turns run by run, so load from elsewhere falls on all of them.
  • Memory is peak anonymous memory sampled every 50 ms, runtime included: Node.js starts tens of megabytes above Rust, and a run under 50 ms may show none.
  • micromark, markdown-it, pulldown-cmark and markdown-rs build no syntax tree; marked, mistune and Python-Markdown are not CommonMark compliant; pulldown-cmark has no GFM autolink literals. The tables compare speed, not features.
