Conformance

One language-neutral corpus of pipeline cases (a pipeline, an input, the expected result) that the Rust, Node and Python implementations all run, in the style of JSON-Schema-Test-Suite. Most cases are ported from upstream unified packages. Counts come from read-only shallow clones of each repo on 2026-10-27; no upstream code was run.

~6.6k cases

hand-written upstream cases after dedupe, WPT included

~1.9k generated

core, markdown, extensions and html surveyed

Layout and format

  • conformance
    • README.md
    • test-schema.json — JSON Schema of a test file
    • tests
      • core
        • use.json
      • md
        • heading-atx.json
      • html
        • sanitize.json
    • sources — importers that turn upstream tests into test files

A file is an array of groups. A group fixes the pipeline; its tests vary the input.

[
  {
    "description": "atx headings",
    "source": {
      "repository": "https://github.com/micromark/micromark",
      "commit": "6577c20",
      "path": "test/io/flow/heading-atx.js",
      "license": "MIT"
    },
    "pipeline": [["md.parse"], ["md.toHtml"], ["html.stringify"]],
    "tests": [
      {
        "description": "rank 1",
        "input": "# a",
        "expected": { "html": "<h1>a</h1>" }
      },
      {
        "description": "no rank 7",
        "input": "####### foo",
        "expected": { "html": "<p>####### foo</p>" }
      }
    ]
  }
]
input / tree
A source string, or a JSON tree for stringify-only and transform cases.
expected.html, .md, .js, .txt
Serialized output, compared exactly, keyed by its file extension.
expected.tree
The resulting tree as JSON, positions in UTF-16 code units; positions: false strips them.
expected.messages
Compared on ruleId, source and place only.
expected.error
A stable code plus an optional substring, never a JS regex.
status: "deviation"
A deliberate difference from upstream, explained in comment.
operations
Core lifecycle cases: use, freeze, data, parse, run, process, each with api: sync | async.

Pending

The corpus is filled before the implementation. conformance/pending.json maps a file, a group or a whole area (md/*) to why it does not pass yet. Runners still run pending cases and tolerate their failures; an entry whose cases all pass fails the run until it is removed, so the list only shrinks.

Runners

  • Rust: rust/textlane/tests/conformance.rs, run by cargo test
  • Node: typescript/-test/conformance.unit.ts, through the loader, on an addon built with --features node,testing
  • Python: python/-test/conformance_unit.py, on a build with python,testing
  • Each keeps its own skip list; a repo guard validates every file against test-schema.json

Test plugins

unified's core tests are about lifecycle. They become data once every implementation has the same built-in test plugins, written once in Rust behind testing: test.parseText, test.compileValue, test.recordOptions, test.replaceTree, test.fail, test.noop, test.appendNode, test.message, test.setData, test.trace, each with a mode (sync, next, deferred, async, promise).

Importers

conformance/sources/<source>.ts turns one upstream repo into test files and records provenance. Inputs are extracted as data (acorn over assert.equal(micromark(…), …) pairs, spec-text splitting, fixture copying); a case whose options hold functions is skipped. Expectations come from upstream verbatim where they describe textlane's path; otherwise from running the reference unified packages once, pinned in the importer's lockfile:

  • HTML regenerated through remark-parse → remark-rehype → rehype-stringify
  • hastscript h() trees expanded to literal JSON
  • trees made for inputs that only had HTML expectations

Imported files are committed; importers are rerun deliberately, never in CI.

Phases

  1. Workspace

    Done: the flat crates textlane, core, md, html, mdx, prose, their features, release config and docs.

  2. Suite skeleton

    Done: conformance/, the schema and its guard, three runners in pnpm test, and a smoke group passing in all three languages through stub test plugins.

  3. Core

    Processor and test plugins; import unified, vfile and unist-util cases.

  4. Markdown

    CommonMark spec, micromark io, from-markdown, to-markdown; then livemark's extensions.

  5. HTML

    to-hast, to-html, rehype fixtures, sanitize, slug, raw; then WPT tree construction.

  6. Prose

    Survey, then import.

  7. MDX

    Survey @mdx-js/mdx; md.mdx, then mdx.compile.

Counts are approximate: leaf test calls and assertions, counted from shallow clones. See Decisions for what is settled.
