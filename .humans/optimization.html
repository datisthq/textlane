Optimization

How much faster textlane can turn Markdown into HTML while staying a unified replacement. Stage times are from 2026-10-29 at commit 9bf4f98, timing parse, run and stringify separately on 1 MB of the benchmark's readme document; library numbers are from the benchmark. The parser's cost is per block and per line, not per byte: one long paragraph runs near 13 MB/s, while a document of tiny paragraphs pays about 2.7 µs each. That is why the benchmark's conformance case, thousands of tiny edge cases, runs at 2 MB/s.

Why comrak is 5× faster with a tree too

Tokenizing
textlane ports markdown-rs (micromark in Rust): a byte-by-byte state machine that tries each construct with attempt and check, saving and restoring its state, and writes an enter/exit event with a position for everything it finds. comrak scans block structure once per line with hand-written scanners and a stack of open blocks.
Between tokens and tree
textlane's resolvers splice the events through an edit map, and content is re-tokenized into text by nested tokenizers before the events become mdast. comrak has no middle layer: nodes go straight into its arena.
Trees
textlane builds mdast, then hast, then serializes hast. comrak renders HTML from its single tree. The second tree and the serializer alone cost textlane 13 ms, about 65% of comrak's whole run.
Not the difference
Memory: both allocate nodes from a per-document arena (bumpalo in textlane-core, typed_arena in comrak), and freeing it is 2 ms of 66.

What unified compatibility forces

Forced
A full mdast with unified's node shapes and positions, since plugins may run between any two stages; a hast as mdast-util-to-hast builds it; HTML as hast-util-to-html writes it. Textlane will never be pulldown-cmark, which builds no tree.
Not forced
The micromark architecture. Only the trees and the HTML are compared, never the events, attempts or tokenizer layers that produce them, so any parser that emits the same mdast with the same positions is compatible.

Ideas

Ordered from safest to largest; each is checked by the conformance suite.

idea Profile the tokenizer and trim per-attempt overhead

Skip the state snapshot on common attempts, shrink events and their points, drop the per-byte check of the shared failure flag, replace the edit map's hash map, and cut re-tokenizing layers where a construct allows it. Keeps the port intact; probably 1.5–2× on parsing at most. Needs perf, which kernel.perf_event_paranoid=1 enables.

idea Skip the hast tree when no plugin needs it

When md.toHtml is followed directly by html.stringify, write HTML from mdast as hast-util-to-html would write the hast, without materializing it. Saves most of the 7 ms; the output is still compared byte for byte, and a pipeline with anything in between takes today's path.

idea Tune md.toHtml and html.stringify

Fewer allocations per node and buffered string writes; small, bounded wins of a few milliseconds per MB.

done A single-pass parser that emits mdast directly

comrak's approach with micromark's output, now md.parse for every extension and MDX: parsing 5–8× faster, the Markdown-to-HTML pipeline 3–5×. The stage times above are from before it.

Not measured yet

  • JavaScript and Python plugins inside a pipeline: each moves a tree across the binding, a cost that depends on the open host-plugin bridge decision.
  • The other pipelines: HTML parsing, md.stringify, MDX and the prose plugins. Only Markdown to HTML is benchmarked.
