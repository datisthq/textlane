Architecture

Textlane replaces unified: one Rust workspace of a few large crates, one per content domain, shipped as one textlane package to crates.io, npm and PyPI. Plugins run natively; existing JavaScript plugins still join a pipeline. The first consumer is livemark.

Rust, Node and Python on one corpus

Crates and their dependencies

rust/Cargo.toml is a virtual manifest; each crate is a sibling directory named by its role, as in fairspec. All crates publish, lock-stepped at one version.

Rules

  • A domain crate depends on textlane-core only, never on another domain or on textlane. Every tree type but the JS tree lives in core, so the bridges need no domain-to-domain edge.
  • The JS tree lives in mdx, the only crate that compiles oxc: oxc parses embedded JavaScript and its ESTree serializer fills mdx's own ESTree store.
  • textlane re-exports the domains as modules and, once it has items, core's items at its root; never as textlane::core, which clashes with Rust's built-in core.
  • Features md, html, mdx and nl are all default; node and python enable every domain.

What each crate holds

textlane
The processor: .with (.use in the bindings), presets, freeze, parse, run, stringify, process, sync transforms with jobs for async work. The bridge that runs JavaScript and Python plugins. The napi and PyO3 bindings. Test plugins behind testing.
textlane-core
unist conventions; mdast (with GFM, math, directive, frontmatter, definition list and MDX nodes), hast and nlcst trees; the file (vfile) and its messages; the plugin contract; visit, is and position utilities.
textlane-md
parse, stringify, gfm, frontmatter, directive, math, definitionList, gemoji, toc, mdx (syntax only), toHtml, toNaturalLanguage.
textlane-html
parse (HTML5), stringify, raw, sanitize, slug, format, toMarkdown, toNaturalLanguage; later katex and highlight.
textlane-mdx
compile: hast into an ESTree tree (embedded JavaScript parsed by oxc), the MDX transforms (document, JSX rewrite, build JSX) and code generation as astring prints it.
textlane-nl
parse (English, Latin), stringify, then smartypants, readability, spell, repeatedWords, passive, equality, contractions, indefiniteArticle, sentenceSpacing, quotes.

One package per registry

Subpaths are views over one native addon. Separate npm or PyPI packages per domain would each need their own addon, and two addons cannot share a tree without serializing it at every boundary.

Rust npm Python
textlane::{Processor, File, …} textlane textlane
textlane::md textlane/md textlane.md
textlane::html textlane/html textlane.html
textlane::mdx textlane/mdx textlane.mdx
textlane::nl textlane/nl textlane.nl 
import { textlane } from "textlane"
import * as md from "textlane/md"
import * as html from "textlane/html"

const processor = textlane()
  .use(md.parse())
  .use(md.gfm())
  .use(md.toHtml())
  .use(html.sanitize())
  .use(html.stringify())

Domains are named short, like file extensions; their functions spell formats out in full: md.toHtml, html.toMarkdown, md.toNaturalLanguage. Names derive mechanically from Rust: to_markdown is toMarkdown through napi's default conversion and to_markdown in Python. Plugin names, their options and node shapes are public API.

MDX across domains

Livemark's compileMDX as a textlane pipeline. Syntax is Markdown's job; compiling to JavaScript is MDX's. Each lane is the crate that owns the stage.

md.mdx finds JSX, expressions and ESM by balanced scanning and keeps them as source strings, so md never compiles oxc. Only mdx parses them.

Hardest points

  1. Reference expectations. micromark's tests assert micromark's own HTML compiler, not the toHtml → stringify path; ~1k expectations are regenerated through unified once.
  2. One addon carries every domain. A tree passed between subpaths must never cross a serialization boundary.
  3. Core holds every tree type but the JS tree. That keeps every domain depending on core alone; the JS tree stays inside mdx.
  4. Lifecycle as data. The core corpus depends on one set of test plugins, identical in all three implementations.
  5. Sanitization is security. One literal case per attack vector, run in every target.
  6. Licences. CommonMark spec text is CC-BY-SA 4.0, WPT BSD-3, github-slugger ISC; each imported group keeps its source licence.
