Architecture

Textlane replaces unified: one Rust workspace of a few large crates, one per content domain, shipped as one textlane package to crates.io, npm and PyPI. Plugins run natively; existing JavaScript plugins still join a pipeline. The first consumer is livemark.

Crates and their dependencies

rust/Cargo.toml is a virtual manifest; each crate is a sibling directory named by its role, as in fairspec. All crates publish, lock-stepped at one version. The dashed edge is optional, behind a feature.

Rules

  • A domain crate depends on textlane-core only, never on another domain or on textlane. Every tree type but JavaScript's lives in core, so the bridges need no domain-to-domain edge.
  • The one exception: html.toJavascript builds oxc's tree, so html depends on javascript behind its javascript feature.
  • textlane re-exports core's items at its root and the domains as modules; never as textlane::core, which clashes with Rust's built-in core.
  • Features markdown, html, prose and javascript are all default; node and python enable every domain; testing adds the conformance test plugins.

What each crate holds

textlane
The processor: .use, presets, freeze, parse, run, stringify, process, sync and async. The bridge that runs JavaScript and Python plugins. The napi and PyO3 bindings. Test plugins behind testing.
textlane-core
unist conventions; mdast (with GFM, math, directive, frontmatter, definition list and MDX nodes), hast and nlcst trees; the file (vfile) and its messages; the plugin contract; visit, is and position utilities.
textlane-markdown
parse, stringify, gfm, frontmatter, directive, math, definitionList, gemoji, toc, mdx (syntax only), toHtml, toProse.
textlane-html
parse (HTML5), stringify, raw, sanitize, slug, format, toMarkdown, toProse, toJavascript (feature); later katex and highlight.
textlane-javascript
The JS tree on oxc (ESTree conversion for JavaScript recma plugins), parse, the MDX transforms (document, JSX rewrite, build JSX), stringify (codegen).
textlane-prose
parse (English, Latin), stringify, then smartypants, readability, spell, repeatedWords, passive, equality, contractions, indefiniteArticle, sentenceSpacing, quotes.

One package per registry

Subpaths are views over one native addon. Separate npm or PyPI packages per domain would each need their own addon, and two addons cannot share a tree without serializing it at every boundary.

Rust npm Python
textlane::{Processor, File, …} textlane textlane
textlane::markdown textlane/markdown textlane.markdown
textlane::html textlane/html textlane.html
textlane::javascript textlane/javascript textlane.javascript
textlane::prose textlane/prose textlane.prose 
import { textlane } from "textlane"
import * as markdown from "textlane/markdown"
import * as html from "textlane/html"

const processor = textlane()
  .use(markdown.parse())
  .use(markdown.gfm())
  .use(markdown.toHtml())
  .use(html.sanitize())
  .use(html.stringify())

Names derive mechanically from Rust: to_javascript is toJavascript through napi's default conversion and to_javascript in Python. A domain name is one lowercase word in every identifier. Plugin names, their options and node shapes are public API.

MDX across domains

Livemark's compileMDX as a textlane pipeline. Syntax is Markdown's job; compilation is JavaScript's. Each lane is the crate that owns the stage.

markdown.mdx finds JSX, expressions and ESM by balanced scanning and keeps them as source strings, so markdown never compiles oxc. Only javascript parses them.

Hardest points

  1. Reference expectations. micromark's tests assert micromark's own HTML compiler, not the toHtml → stringify path; ~1k expectations are regenerated through unified once.
  2. One addon carries every domain. A tree passed between subpaths must never cross a serialization boundary.
  3. Core holds every tree type but JavaScript's. That keeps bridges free of domain edges; html.toJavascript is the only exception.
  4. Lifecycle as data. The core corpus depends on one set of test plugins, identical in all three implementations.
  5. Sanitization is security. One literal case per attack vector, run in every target.
  6. Licences. CommonMark spec text is CC-BY-SA 4.0, WPT BSD-3, github-slugger ISC; each imported group keeps its source licence.
