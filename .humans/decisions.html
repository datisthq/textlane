Decisions

What has been settled about textlane's structure and its conformance suite, who settled it, and what was turned down. Sources: the "Review Unified Rust Architecture" planning chat, the session that wrote the design spec and the trees-and-plugins design session. As of 2026-10-28.

Product and scope

decided Textlane is a unified replacement whose first job is powering livemark

Why. Livemark's plugin set is the first compatibility target; breadth comes after.

Rejected. Porting the whole ecosystem up front.

decided Textlane owns its Markdown parser

Why. The goal is to replace markdown-rs, not wrap it; MDX is designed into the grammar from the start.

Rejected. Building on markdown-rs, which stays a behavioural reference and a test source.

decided MDX, KaTeX and Shiki output parity come later

Why. Package structure and conformance first.

Rejected. Starting from livemark's compileMDX.

Packages and names

decided A cargo workspace of a few large crates, one per domain

Why. Crate boundaries keep the tree crate separate and let Rust users skip domains.

Rejected. One crate per plugin; one single crate.

decided Flat layout: a virtual rust/Cargo.toml and one sibling directory per crate

Why. Matches fairspec; no root-package special case.

Rejected. A root package with members under crates/.

decided One package per registry, a subpath per domain

Why. Each binding is one addon; separate addons cannot share a tree without serializing it.

Rejected. @textlane/markdown and @textlane/html as separate npm packages.

decided Crate names core, md, html, mdx, prose

Why. Domains are named by their format, short like file extensions (md, html, mdx), with prose for natural language; core also holds the plugin contract every domain implements.

Rejected. ast, model, data, tree; markdown; javascript, script, ecmascript; text, nl, language, nlcst, article; the upstream remark, rehype, retext and recma prefixes.

decided Plugins are namespaced by domain: md.parse(), html.sanitize()

Why. Large crates export clashing names (parse, stringify); namespace imports keep them short.

Rejected. Prefixed exports such as markdownParse; * as md.

decided Domains are named short; functions spell formats out in full: md.toHtml, html.toMarkdown, md.toProse

Why. Short namespaces read well in pipelines; full function names stay clear and derive mechanically: Rust to_markdown, napi toMarkdown, Python to_markdown.

Rejected. Abbreviated bridges such as toMd or toJs; toJavaScript, which needs a js_name override.

decided MDX syntax in md (md.mdx), compilation in the mdx crate (mdx.compile)

Why. Syntax changes how Markdown tokenizes; compiling hast to a JS module is its own format's job, as @mdx-js/mdx is upstream. The JS tree on oxc stays internal to mdx, and no domain depends on another.

Rejected. A javascript (or script) crate with html.toJavascript, which needed an html → javascript edge and made a general JS tree public API; MDX compilation inside md behind a feature.

my call Every tree type but the JS tree lives in core

Why. Bridges then need no domain-to-domain dependency; the JS tree is oxc's and stays inside mdx.

Rejected. Each domain owning its tree types.

Trees and plugins

Detail on Trees and plugins.

decided Speed in Rust settles every trade-off; JavaScript and Python plugins are a last resort

Why. Native pipelines pay nothing; a foreign plugin pays a conversion at its boundary.

Rejected. Optimizing the tree for cheap access from JavaScript.

decided The parser is a port: micromark's design, markdown-rs as the Rust reference, in textlane's own layout

Why. micromark keeps the extension model markdown-rs flattened; markdown-rs shows each state machine in Rust; the corpus makes a port safe.

Rejected. Vendoring markdown-rs and reshaping it; a clean-room design.

decided Crates follow fairspec's layout (models/, actions/, helpers/, plugins/) plus utils/<name>/ for bounded internal systems

Why. A tokenizer or serializer is many mutually recursive functions that cannot be one action per file.

Rejected. A layout of upstream-named layer modules (syntax/, from_markdown/…).

my call md entities are constructs or mdast nodes; verbs are the layers: tokenize, resolve, compile, stringify, convert

Why. One folder holds everything about a construct, and each verb names its upstream package.

Rejected. to_hast as a verb; one file per upstream module.

decided Trees are structurally unified's: same node types, fields and nesting

Why. Standard trees serialize to the exact JSON unified produces, which the corpus pins.

my call Typed enum trees in a per-document bump arena, strings borrowed from the input

Why. Allocation is a pointer bump and drop is one free, with a normal &mut tree API; the price is the 'a lifetime on every Rust plugin.

Rejected. Owned enums with compact strings (simpler, an estimated 1.5–2× parse and drop cost); an index arena (as fast, but tree[id] bookkeeping).

my call Positions are two u32 byte offsets, with a boxed full unist position as fallback; UTF-16 is computed at the edge

Why. 8 bytes per node; the decided UTF-16 positions are what serializing and foreign plugins see.

Rejected. Storing line, column and UTF-16 offset on every node.

my call Fidelity slots: a per-field null-or-omit rule, Node::Unknown, hast properties as a short inline list, one extra box per node for data

Why. Covers where unist is looser than a typed tree, at one null pointer per node when unused.

Rejected. A hash map per element for properties; no escape hatch for unknown nodes.

decided Rust composes with .with(); the bindings keep .use()

Why. use is a Rust keyword; unified's users meet .use() in JavaScript and Python, where it is free; .with() has tracing-subscriber's precedent.

Rejected. .r#use(), .use_(), .plugin(), and .add(), which clippy's should_implement_trait flags.

my call Freeze attaches each plugin once into typed slots; Tree is an enum whose stage kinds freeze() checks; options derive Deserialize; presets are plugins

Why. All setup happens once, a frozen processor is Send + Sync, and plugin lists stay dynamic for livemark's config and the bindings.

Rejected. String-keyed data() natively; a type-state processor checked at compile time.

decided Transforms are sync; setup may be async; per-document async work goes through jobs, filled after process()

Why. Pausing on a JavaScript promise needs a self-referential arena and tree moved across threads; Shiki is async only to load, and fetches, link checks and Mermaid yield fragments. One batch per site beats one browser per run.

Rejected. Async transforms everywhere; async JavaScript plugins mid-pipeline in v1.

my call Foreign plugins are transforms only in v1, each run on a converted copy; consecutive foreign stages share one conversion

Why. A live handle into the arena would tie JavaScript objects to a tree that dies with process().

Rejected. A live handle; foreign parsers and compilers.

Conformance suite

decided One language-neutral corpus in the style of JSON-Schema-Test-Suite, run by Rust, Node and Python

Why. The suite is the contract; no expected results are copied per implementation.

Rejected. Separate test suites per binding.

decided Cases are input, pipeline and output only; each implementation keeps its own unit tests

Why. A pipeline library's contract is what it produces.

Rejected. Asserting internals in the corpus.

decided Layout and format follow fairspec's conformance/

Why. One in-house convention: test-schema.json, tests/<area>/<feature>.json, groups of tests.

decided Positions count UTF-16 code units, as unified's do

Why. Upstream trees import verbatim; JS plugins see unified-identical positions; the crate converts at the edge.

Rejected. Bytes; code points.

decided Serialized output is keyed by its file extension: expected.html, .md, .js, .txt

Why. A case reads self-describing, and the key names what the string is, not which domain made it: mdx.compile yields js, prose.stringify yields txt.

Rejected. One generic text key; .markdown; .prose.

decided Ported groups follow upstream's grouping: one group per spec section or test block

Why. Files read like the upstream suite, and a section shares one pipeline.

Rejected. One group per example.

decided Test files are named by construct (md/heading-atx), with a group per source inside

Why. unified groups its tests by construct within each package; one file then holds all coverage of a construct, and provenance stays in each group's source.

Rejected. One file per upstream source and section (md/commonmark-atx-headings).

decided Every CommonMark example is also a tree case: md.parse to the mdast unified produces, positions included

Why. Pins mdast shapes and UTF-16 positions for every spec construct, not only the HTML they render to.

Rejected. Tree cases from from-markdown alone; trees for every micromark input too.

decided WPT tree-construction and html5lib serializer cases are converted into test files; the html5lib tokenizer suite is not ported

Why. Conversion follows the same importer pattern; the tokenizer is internal, not a plugin.

Rejected. Vendoring .dat files behind a loader; porting the 6,827 tokenizer cases.

decided The corpus is filled before the implementation; conformance/pending.json marks what the crate does not pass yet

Why. Implementation then works against a complete target, and the list records progress.

Rejected. Porting tests alongside each feature.

decided Importers may run unified once to produce expectations; comparison is always exact

Why. micromark asserts its own HTML compiler, which textlane does not have; regenerated expectations are exactly what textlane must produce.

Rejected. An HTML-equivalence compare mode with a parser per runner.

my call Test plugins are written once in Rust, behind textlane's testing feature

Why. One copy every runner reaches; nothing ships them.

Rejected. Rewriting them in JavaScript and Python.

my call Phases 1–2 (workspace, suite skeleton) are planned in full; phases 3–7 stay a roadmap

Why. Later phases are whole parsers; each is planned when it starts.

Rejected. One plan for everything.

my call Runners skip lifecycle modes they cannot express until the processor's async model exists

Why. Keeps the suite runnable before the processor is designed.

my call Phase 2 drives the suite through a stub: run_case with test.parseText and test.compileValue, behind testing

Why. Proves the format, the schema guard and all three runners before the processor and tree types are designed in phase 3; test files stay unchanged when the stub goes.

Rejected. Designing the processor and the tree types in phase 2.

my call Pending is strict: pending cases run and may fail, an entry whose cases all pass fails the run until removed; an area wildcard trips only once its whole area passes

Why. Keeps pending.json an exact record of what is unimplemented without forcing early wildcards apart.

Rejected. Report-only, which lets the list go stale.

my call Importers skip what a pipeline case cannot express (options without a textlane equivalent, non-literal input, lone surrogates) and report the counts

Why. Keeps imported cases honest; the skipped ones come back when the option they need is designed.

Rejected. Inventing public options to carry them now.

my call md.stringify options keep mdast-util-to-markdown's names (bullet, fence, setext, listItemIndent, unsafe…)

Why. They are remark-stringify's public options already, so ported cases and migrating users need no mapping; the same choice allowDangerousHtml made.

Rejected. Renaming them now, before any implementation exists.

my call md.gfm options keep remark-gfm's names (singleTilde…), and footnote rendering options sit on md.toHtml under remark-rehype's (clobberPrefix, footnoteLabel…)

Why. Each option lives on the plugin whose upstream counterpart owns it, under that counterpart's name.

Rejected. One combined options object on md.gfm.

my call Verbatim upstream expectations follow upstream's latest release, even while the pinned reference still lags it

Why. mdast-util-to-markdown 2.2.1 (2026-10-27) changes 21 expectations the quarantined 2.2.0 reference would get wrong; the corpus should not encode a superseded release.

Rejected. Rendering every expectation through the lagging reference.

my call micromark-extension-directive's inputs port as tree cases, not HTML cases

Why. Unhandled directives vanish from micromark's HTML and fall back to a div in unified's; the mdast is what livemark's directive plugins consume.

Rejected. HTML cases that only test mdast-util-to-hast's unknown-node fallback.

my call md.directive options adopt mdast-util-directive's serializer names (quote, quoteSmart, preferUnquoted, preferShortcut, collapseEmptyAttributes)

Why. remark-directive takes no options; the serializer that owns them names them.

Rejected. Leaving the serializer options unreachable.

my call Math ports without KaTeX: micromark's inputs as tree cases, remark-math's HTML as the math-inline / math-display code elements md.toHtml emits; md.math keeps remark-math's singleDollarTextMath

Why. micromark's expected HTML embeds KaTeX's output, a renderer textlane defers.

Rejected. Freezing KaTeX's output into the corpus.

my call Invalid plugin options fail with one shared error code, invalid-options, and upstream's message as the substring to match; md.frontmatter takes remark-frontmatter's options whole (a preset, a matter or a list)

Why. Error codes are public API: one per kind of failure keeps them stable while messages stay free to change.

Rejected. A code per upstream message.

my call Gemoji stores a case for every name in gemoji's table (1,915), not a sample

Why. The table is the plugin's behaviour; full coverage proves textlane embeds the same one, at about 340 KB.

Rejected. Generating cases at test time; a sample.

my call Each runner skips only through a KNOWN_DIVERGENCES map of group to open issue, as fairspec's do

Why. A skipped case always points at the fix that unblocks it.

Rejected. Free-form skip lists.
