Trees and plugins

The tree shape and the plugin contract every crate builds on, and the layout of the md crate that ports micromark. Source: the design session of 2026-10-28; the bootstrap implements the arena tree, positions, the processor, html.stringify and md's engine with paragraphs, ATX headings and thematic breaks; the rest is design. Each choice's status and the alternatives turned down are on Decisions.

The goal that settles every trade-off: be the fastest pipeline in Rust. JavaScript and Python plugins are a last resort for exotic needs, so they pay a conversion at the boundary and native plugins pay nothing.

The tree

Typed enums

mdast::Node<'a> and hast::Node<'a> have a variant per node type (Heading(Box<'a, Heading<'a>>)…), so plugins match exhaustively and never compare type strings.

One bump arena per document

Every node is allocated in an arena (bumpalo, as oxc does): building a node is a pointer bump, dropping a tree is one free, siblings sit together in memory. Children are ArenaVec<'a, Node<'a>>.

Zero-copy strings

value: &'a str borrows the input where it can; decoded or joined strings are allocated in the arena.

Positions: two byte offsets

A position is two u32 byte offsets, 8 bytes; the top two bits of each hold the virtual spaces into a tab, which unist counts in columns. Line, column and the UTF-16 offset unified reports are computed only at the edge (serializing, diagnostics, foreign plugins) from a line index on the file. A position that does not point into the current source, such as one a JavaScript plugin set by line and column alone, falls back to a boxed full unist position.

The price

Every Rust plugin carries the 'a lifetime; a tree cannot outlive its allocator (md::parse(&alloc, input)); anything stored in a node lives in the arena or is 'static; one tree stays on one thread at a time, and parallelism is across documents.

Structurally unified's

Node types, field names and nesting are unified's, so a standard tree serializes to the exact JSON unified produces; the corpus pins it. unist is looser than a typed tree in four places, each handled on purpose:

Null or absent

from-markdown emits title: null and omits other optional fields. Each Option field carries a fixed rule, copied from unified's output, for whether None serializes as null or is left out.

Unknown node types

Node::Unknown holds a type name and a JSON-like value, so a node a foreign plugin invents survives the pipeline.

The extra slot

Each node has extra: Option<Box<Extra>>, one null pointer when unused. It holds data (typed hName, hProperties, hChildren plus an open map) and is where unknown top-level fields would go. For now conversion drops those with a warning; filling the slot later changes no node shape.

Values only JavaScript has

hast property values get their own enum (string, number, boolean, lists, null) in a short inline list, not a map. Functions or class instances in data cannot cross and fail the conversion. MDX's data.estree is attached by mdx when a foreign plugin needs it, since md has no JS parser.

The processor

  1. Compose

    Processor::new().with(md::parse()).with(md::gfm()).with(md::to_html()).with(html::stringify()). Rust says .with(); the bindings keep unified's .use().

  2. Freeze, once

    Each plugin's attach runs once and does all setup: md::parse merges every registered syntax extension into one table of constructs by character code, and the stage sequence is checked. Setup may be async (loading grammars or a highlighter).

  3. Process, many times

    A frozen processor is Send + Sync. Each process(&self, input) gets its own arena, so a site build is a parallel map over files with no locks.

The attach context

set_parser, add_transform, set_compiler, and cross-plugin data in slots keyed by type in place of unified's string-keyed this.data(): md::gfm pushes into md::Syntax and md::Handlers, which md::parse and md::stringify read. Plugin order is free, as in unified.

Stages

enum Tree<'a> { Mdast, Hast, Prose }. Every plugin declares the kind it takes and returns, and freeze() rejects a mismatch. Plugin lists stay dynamic, as livemark's config and the bindings need; the check costs one match per stage, not per node.

A transform

fn run<'a>(&self, tree: Tree<'a>, file: &mut File, alloc: &'a Allocator) -> Result<Tree<'a>, Error>: it takes the tree and returns one, so a bridge such as md.toHtml returns another kind.

The file

Input, path, the line index, metadata, vfile-style messages (file.warn(reason, position, rule)) and the job list. A fatal error stops the pipeline as an Err.

Options

One struct per plugin deriving Deserialize; the bindings fill it from a plain object, with names converted mechanically. No per-binding option code.

Presets

A plugin whose attach attaches others.

Where it lives

The plugin contract, Tree and File in textlane-core; the processor and the foreign-plugin conversion in textlane, as Architecture lays out.

Foreign plugins

A JavaScript or Python function joins a pipeline as a ForeignTransform, and in v1 only as a transform: no foreign parsers or compilers. At its stage the tree is converted into unified-shaped objects, UTF-16 positions included, the function runs, and the result is rebuilt into the arena. Consecutive foreign stages share one conversion. The cost is linear in the tree, paid only where a foreign plugin sits.

Async and jobs

Transforms are sync. napi calls JavaScript only on the main thread, so pausing a pipeline on a JavaScript promise means keeping an arena and the tree borrowing it alive across the pause, a self-referential pair moved between threads. Few plugins need it: Shiki's @shikijs/rehype is async only to load grammars, and @shikijs/rehype/core with a prepared highlighter is sync. The genuinely per-document async plugins fetch, lint links or render in a browser, and those produce a fragment of output.

  1. Emit

    A sync transform replaces the work with a placeholder (<!--textlane:job:3-->) and records a job, {kind, payload}, on the file.

  2. Return

    process() finishes and returns the output with its jobs; the arena is already gone.

  3. Resolve

    The host resolves every job from every document in one async batch: one browser session renders a whole site's Mermaid diagrams, where rehype-mermaid launches one per run.

  4. Fill

    fill(output, results) splices the results in.

A job can only yield a fragment; it cannot reshape the tree after the async step. A fully pausable pipeline waits until a real plugin needs that.

The md crate

A port of micromark and the mdast utilities: micromark (JavaScript) for the design, since it keeps the extension model, and markdown-rs for how each state machine reads in Rust. Both are MIT, so ported code keeps their attribution. The layout follows fairspec's, plus utils/:

  • rust/md/src
    • lib.rs — the module tree, inline
    • plugin.rs — the extension contract: constructs, compile and stringify handlers
    • models — codes, events, token names, the construct trait, options
    • utils — bounded internal systems, exempt from one action per file
      • tokenizer — the micromark engine: driver, content types, subtokenize
      • compiler — events to mdast
      • serializer — mdast to Markdown: join, safe, unsafe patterns
      • converter — mdast to hast, footnotes
    • actions — one handler per file, entity by construct or node
      • markdown/parse.rs, markdown/stringify.rs, mdast/convert.rs
      • heading_atx/tokenize.rs
      • heading/compile.rs, heading/stringify.rs, heading/convert.rs
      • attention/tokenize.rs, attention/resolve.rs
    • helpers — UTF-16 positions, characters, identifiers, references, URIs
    • plugins — every public stage: parse, stringify, to_html, gfm, math, directive, definition_list, frontmatter, mdx, gemoji
Verb Upstream One file holds
tokenize micromark a construct's state machine
resolve micromark resolvers event post-processing
compile mdast-util-from-markdown events into one node
stringify mdast-util-to-markdown one node to Markdown
convert mdast-util-to-hast one node to hast

CommonMark sits at the top level and registers through the same contract as gfm, which proves the contract sufficient; extensions reuse its partials (label, destination, space_or_tab). An extension plugin bundles syntax, compile and stringify handlers, as remark-gfm bundles its micromark and mdast-util halves. MDX syntax finds where {…} ends by counting braces, micromark's own fallback without acorn, so md never needs oxc.

Hardest points

  • Container continuation and lazy lines in block quotes and lists, with subtokenizing
  • The attention resolver behind emphasis
  • Precedence between extensions on one character code: : starts directives, GFM autolinks and definition lists
  • to-markdown's unsafe-pattern escaping
  • Exact UTF-16 positions through tab virtual spaces
  • The corpus's lifecycle cases written for unified's async modes; under sync transforms they become deviations
